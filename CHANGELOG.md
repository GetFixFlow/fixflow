# Changelog

All notable changes to FixFlow CMMS will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

- Email settings work (Day 9). Settings, Email never worked: the page had no server behind it, and it showed an empty form even when something was saved. Administrators can now enter the mail server (with presets for Microsoft 365, Gmail and a network server), send themselves a test email through what is in the form without saving it, and see the reason in plain words when it fails (wrong password, unknown host, nothing listening, wrong encryption). Saved settings (password stored encrypted, never shown again) are used for every email, ahead of the `SMTP_*` environment settings, and take effect without a restart. Changes are written to the audit log. **Run `rails db:migrate`.**
- Open-source basics (roadmap p07): `CONTRIBUTING.md` (how to set up, what a pull request needs, the checks CI runs, and the mistakes that have already cost time), `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1), `SECURITY.md` (what to report, what is in scope, how to keep an install safe), an issue chooser with bug-report and feature-request forms that points security reports at GitHub's private reporting, and a pull request template that asks what was not tested. Security and conduct reports go through GitHub's private vulnerability reporting, so no email address is published; the repository setting for it has to be switched on by an owner.
- The server checks its settings when it starts (roadmap d05). A missing secret used to crash the boot with a bare `KeyError: key not found`, a copied `.env.example` ran happily with its example passwords, a wrong database address made the Docker entrypoint wait for ever, and a mistyped `APP_URL` or `ALLOWED_ORIGINS` showed up later as broken email links or a blocked browser. Now a production server (and Sidekiq, and the Docker entrypoint, before it migrates anything) refuses to start with a plain message when `SECRET_KEY_BASE` or `DEVISE_JWT_SECRET_KEY` is missing, too short or an example value, when `DATABASE_URL`, `REDIS_URL`, `APP_URL`, `ALLOWED_ORIGINS`, `SMTP_PORT`, `MQTT_PORT` or `MINIO_ENDPOINT` is malformed or carries an example password, or when the database, Redis or the mail server set in the environment does not answer. Less serious things (no `APP_URL`, example storage, broker or mail passwords, `SEED_DB=true`, a missing AI key, the file storage or broker not answering) are printed as warnings. `bin/rails fixflow:check_config` runs the same check by hand (`[static]` skips the network), `SKIP_CONFIG_CHECK=true` turns it off, and the entrypoint now gives up waiting for the database after two minutes with a message. The README's variable table, which named variables the code does not read (`CORS_ORIGINS`, `RAILS_MASTER_KEY` for production), is rewritten from what the code reads, and `.env.example` says which settings are required.
- The PM Compliance report counts missed maintenance and obeys the Filters; every report is checked against the server's real answer. PM compliance only counted skipped and completed maintenance, so maintenance that came due and was never done did not count against it (a company that ignored its PMs could show 100%); it now uses the PM dashboard's definition (skipped and missed count against it, not-yet-due is left out, "—" when nothing came due) in the totals, by month, by place and by asset. The report and its forecast now apply the assets, places and people in the Filters panel, the forecast's Freq. column shows how often each schedule repeats (it was always a dash), and the cards show skipped and missed together. The Asset Health and PM reports no longer hold their figures in a cache that nothing ever cleared, so finished work shows at once. **Changed answer:** `GET /reports/pm/compliance` now has `summary.missed` (it had `summary.overdue`), `missed` in each month and place, and null rates. The PM, IoT and Cost report answers join the golden-fixture check (`spec/contracts/report_shapes_spec.rb`), the PM, IoT and Cost screens now read typed answers, and their tests render the real pages with the saved answers; the IoT trend's `resolved` is what the chart is typed to read.
- The dashboard works for technicians and requesters. The server has always sent them different answers (their own work, their own requests), but the page read only the manager's, so it failed for everyone who is not a manager or administrator; it now shows a technician their assigned, in-progress, overdue and completed-today work, their upcoming maintenance and activity, and a requester their open and completed requests. Also fixed for managers: the PM Compliance card ignored missed maintenance (a company that never did its PMs could show 100%) and now uses the PM dashboard's figure, with "—" when nothing came due; "Due this week" no longer counts overdue schedules a second time; the average hours to finish is a number, not text; and the figures are no longer held in a five-minute cache that nothing ever cleared, which made finished work look unfinished. The three answers are covered by the golden-fixture check (`spec/contracts/report_shapes_spec.rb`).
- The Work Orders, Asset Health and Technician Performance report screens show real figures. They read fields the server never sent, so on real data the Work Orders cards were zero, the MTTR and backlog charts were empty, the Asset Health cards, donut, cost chart and inventory were empty or wrong, and the asset panel was hard-coded zeros. The server now sends what the charts draw (by-priority detail, a trend of created, completed and resolution hours, a 13-week completion heatmap, MTTR by asset, place and technician, backlog ages and the oldest open work orders, an asset inventory, and an asset's monthly history), as numbers rather than text; the screens read the server's field names; and Asset Health and Technician Performance now apply the Filters panel (and send the period), as do their files. Days, weeks and months in these reports are the company's time zone, not UTC. MTTR no longer counts work orders that were never started. The response shapes are pinned from both ends by golden fixtures (`spec/contracts/report_shapes_spec.rb` and typed web tests). Changed responses: `GET /reports/work_orders/mttr` now returns `overall_avg` and `by_group` (it returned `overall_mttr_hours`, `by_asset`, `by_technician`, `by_location`), `GET /reports/work_orders/backlog` returns `aging` and `oldest_wos` (it returned `aging_buckets`, `oldest_work_orders`), and asset history figures are numbers.
- The backend specs now run in CI. Until now CI ran only the style check, the security scans and the web app's checks, so the 1,200+ backend specs ran only on a developer's machine and nothing stopped a pull request from breaking them. A new `test` job runs them against a real PostgreSQL 16 and Redis 7 with the schema loaded fresh. Its first run failed on one spec that needs Redis (`fixflow:stats`), which had gone unnoticed because Redis was running on the developer's machine; the job now provides it. No migration.
- A check that the web app and the API agree: `bin/rails web:check_routes` reads every request the web app makes (from its TypeScript source, including the report downloads) and fails if Rails has no route for one, if a request builds its address from a variable (so it cannot be checked), or if an API route leads to a controller action that does not exist. It runs in CI (a new `web_routes` job: needs Ruby and Node, no database), with an allowlist (`config/web_routes_allowlist.yml`, each entry with a reason; unused entries are reported). Dozens of requests (45 of 121 when first counted) had been written for endpoints that did not exist, which this would have caught the day they were written; today all 145 requests have a route. It does not check the shape of what an endpoint returns. No migration.
- IoT monitor, IoT report and live alerts work (second half of the IoT screens). The IoT Monitor asked for `/reports/iot/dashboard`, which did not exist, and showed an all-zero "All clear" when it failed; it now shows the real figures (active sensors, readings per hour and the change, open alerts by severity, active and triggered rules, the latest value of each metric on each asset with how close it is to its limit, a week of hourly activity) or an error with Try again, and its "Updated ... ago" is the real fetch time. The IoT Analytics report asked for `/reports/iot/alerts` and `/rule_effectiveness`, which did not exist: both are built (total, critical, open, work orders, share resolved, a daily or weekly trend by severity, per-rule results, and one asset's daily metric averages), follow the Filters panel, and export a CSV of the alerts (spreadsheet formulas in names are saved as text). Its "Auto-Resolved Rate" is now "Resolved Rate", because nothing resolves alerts automatically. **Live alerts never worked**: the browser listened on channels the server did not have (`IoTAlertChannel`, `AssetSensorChannel`), connected to `/cable` without the sign-in token the server requires, and the header bell's mark was never cleared. There is now an `IotAlertChannel` that streams a company's alerts to its own members only, the browser connects with its token, listens on the right channels, shows toasts for critical and high alerts anywhere in the app, refreshes the lists and the monitor, shows Live/Offline truthfully, and the bell takes you to the alerts and clears its mark. Readings carry `sensor_type` (the name the asset IoT screen groups by), and the asset IoT page's live readings use the server's payload. Also fixed: the alert summary report counted resolved alerts as 0 (the enum-name comparison fixed for PM compliance). Removed: the unused readings-activity call. No migration. **Your proxy must pass WebSocket upgrades on `/cable`, and the background worker must be running for live alerts.**
- IoT alert and rule actions work (first half of the IoT screens). Suppress, bulk acknowledge and bulk resolve, an asset's alert history, archive and duplicate for rules, and the rule test box called endpoints that did not exist or sent and read different field names, so none of them could work; creating a rule from the form failed because the form sends `threshold_value`, `metric_unit`, `sustained_minutes` and `wo_assignee_id` while the server wanted `threshold`, `unit`... Both sets of names now work, and alerts and rules are also sent with the names the screens read (`severity`, `message`, `sensor_value`, `rule_name`, `location_path`, `threshold_value`, `metric_unit` ...). An alert's severity is its rule's priority. Alerts now move only along open, acknowledged, resolved (suppressed can be resolved): acknowledging an already acknowledged alert used to count it again against its rule, and a resolved alert could be "acknowledged". A duplicated rule starts paused. The test box answers in words and shows the last readings; a value that is not a number is refused instead of being tested as 0. A rule's assignee must be an active person in the company. Date filters on the alert list (`from`, `to`) failed with a server error (ambiguous column) and now work, with 400 for a date it cannot read. Failures on these screens are now shown (before, a refused action showed nothing) and the alert list reloads after one. No migration. Not yet done: the IoT dashboard, readings activity and IoT reports.
- Report export works (Export menu on the report pages). The CSV and PDF buttons did nothing or were missing: the web asked for `/reports/<type>/export.csv`, which never existed; three pages had an Export menu with nothing behind it; and the exports the server did have were wrong (the work order CSV was filled with trend rows under work order headings, the asset health CSV had nine headings and seven columns). Now Work Orders, Asset Health and PM Compliance export a CSV and a PDF, Cost Analysis (every asset, not just the top 20) and Technician Performance a CSV, all made by the server with the same dates and filters as the screen, for managers and administrators. The work order CSV lists the work orders themselves (cut at 50,000, and the page says when it was). Files open in Excel with accents kept. **Security:** text that starts with `=`, `+`, `-` or `@` (work order titles can come from the public request form) is saved as text, so it cannot run as a spreadsheet formula. **Also fixed:** the PM Compliance report's monthly, by-place and worst-asset breakdowns always showed 0 completed, 0 skipped and 0% (the totals were right); and the asset health and PM compliance reports could show one filter's figures for another's request, because the cache did not include the filter. The IoT report still has no export. No migration.
- You can see where you are signed in and end any session (Settings, My Profile). The list had no server behind it, and the old design (one token marker per person) could not have had one: signing out anywhere signed you out everywhere. Each sign-in is now its own session, shown with the device ("Chrome on macOS"), its address and when it was last used; you can sign out of one session or of all the others, and ending one is written to the activity log, and an ended session cannot open a new live-update connection (one already open stays until the page is reloaded). **Signing out now ends only that session** (before, it ended all of them). Changing your password or being deactivated still ends every session. The made-up "Location" column was replaced by the address the server sees. A browser's description is cut to 255 characters and cleaned before it is stored: text with invalid bytes or a null byte would otherwise have made sign-in fail. **Run `rails db:migrate` (`user_sessions`). Everyone signs in once more after upgrading**, because tokens made before this change have no session behind them.
- Notification preferences work (Settings, Notifications). The page had no server behind it and promised much more than exists: nothing saved, and the switches for push, in-app notifications, daily digest and weekly report had nothing behind them (no push sending, no notification store, no digest jobs), so they were removed rather than saved and ignored, and the alert sound switch never did anything. Everyone can now choose which emails they get: one master switch and one tick for each email the app really sends (assigned to me, my request finished, needs verifying, problem reported from a QR label, scheduled work order for me, maintenance due or overdue, part low or out). Every send checks the choice, so an email switched off is not sent; the default is everything on, as before. Invitations and password reset links are always sent. The alert sound switch now works and applies to that browser. Found on the way: several emails to managers (new problem reports, work awaiting verification, overdue and due maintenance) also went to deactivated managers; deactivated people are now never emailed. **Run `rails db:migrate`** (`users.notification_preferences`).
- Anyone can report a problem by scanning an asset's QR label, without an account (roadmap p10). The public form and status page (`/request`, `/request/<link>`) called `/work_requests`, which did not exist (an old unfinished `/requests` stub was routed instead and never worked: it needed a subdomain, had no limits, and the form hid every failure behind a made-up "REQ-demo" confirmation, so a request that was never sent looked sent). It is now built for strangers: an unguessable link per request (128 random bits) that shows only progress, never names, emails, costs, comments or other work orders; labels carry a random per-asset code instead of the sequential id; field size limits, a 16 KB body cap, control characters removed, a hidden trap field for scripts, and throttles (5 reports per 10 minutes and 20 a day per address, 60 an hour overall, 60 lookups per 5 minutes). Failures are shown as failures (too many requests, too long, no connection). The company's default priority and due date apply; the caller cannot choose them. QR labels now link to the public form (**reprint labels printed before this**); signed-in staff scanning one are taken to the asset. Email is optional on the form. New: `assets.public_code` (**run `rails db:migrate`**). Removed: the unfinished `POST/GET /api/v1/requests` routes and the made-up "ext. 200" emergency number on the form.
- Cost reports work, the report Filters panel works, and reports are closed to non-managers on the server. The Cost Analysis page asked for three endpoints (`/reports/costs/summary`, `by_asset`, `by_location`) that did not exist: they now do, counting completed and verified work by the date it was completed, with labor and parts apart, a trend whose bucket (day, week, month) follows the length of the period, a treemap and a by-place breakdown. The Filters panel sent lists (places, assets, people, priorities, sources) that no server code read, so it did nothing on any report; the shared report code now applies them (places include what is inside them, and a source is derived from whether a work order came from a schedule, an IoT rule or was made by hand), also for the work order reports. **Security:** since labor cost became real, most report endpoints (`assets/cost_analysis`, asset health, work order summaries...) would have shown wage totals to any signed-in user who called them directly, because only one report action checked the role. All report endpoints now require a manager or administrator, as the screens already did. The cost page also now says when nothing was finished in a period or when the figures could not be loaded, and its trend axis follows the company's date format.
- Sample data and a real first-steps guide (Day 17). Administrators can add sample data to their own company (Settings, Import / Export, the dashboard, or `rails fixflow:sample_data`): a few places, assets, parts, a PM schedule with a checklist and open and finished work orders, all named "Sample: ...", creating no accounts and sending no email (it deliberately does not go through the PM scheduler, which would email the technician). Every record is tracked, so it can be removed again in one click or `rails fixflow:remove_sample_data`: sample items you have since built on are kept and listed, together with the places they sit in (removing a place removes what is inside it, which the removal now guards against). The dashboard shows administrators a Getting started card with three first steps ticked off from real data (sample data does not count), and a note while sample data is loaded. The 500-line onboarding wizard was removed: it saved nothing (it kept names, locations and invites in the browser only) and nothing linked to it. The separate demo company (`fixflow:demo_data`, with known passwords, for trial installs) is unchanged. **Run `rails db:migrate`.**
- CSV import for locations, assets and parts (Day 16). The old asset import page was a mock-up: a hand-rolled parser that broke on any comma in a value, creating assets one request at a time, with no locations or parts and nothing to stop the same file being imported twice. Import is now done by the server: pick what to import, download a template, upload your file and see a preview (or every problem, each with its spreadsheet row and column), then import. A file with any problem imports nothing, so a corrected file can be uploaded again without doubling rows. It reads files as Excel writes them (byte order mark, Windows line endings and encoding, `;` or tab separators, quoted commas and line breaks), finds a location by name or full path (`Plant > Floor 1`), refuses duplicate asset tags and part SKUs (in the file or already in use), keeps extra asset columns as custom fields, and is audit-logged. Managers and administrators only. `/assets/import` now goes to the new page, and Import buttons were added to Locations and Parts.
- Checklists work end to end (Day p11, second half). The checklist on a work order never appeared: the page read a field the server does not send. It now shows, with progress and who ticked each step and when. The server now refuses to complete a work order while a required step is undone (naming the steps; a step is required unless marked optional), and keeps a finished work order's checklist as it was. Ticking a step shows at once, is sent as just that step, works offline (kept on the phone, marked "Waiting to sync") and a retry does not change who or when. Managers can tick steps as well as the assigned technician; the tick targets are larger for phones.
- Labor cost is calculated (Day p11). `work_orders.labor_cost` was never filled in, so every cost report showed zero labor, and the work order screen made up a fixed 40 an hour. Labor is now the recorded hours times the assignee's hourly rate, or the company's default rate (Settings, Company) if they have none; admins can set a person's own rate (Settings, Users, Edit). The rate used is kept on the work order, so later rate changes do not rewrite history. Cost reports include labor. Labor costs and rates are shown to managers and administrators only, since they reveal pay; others see the parts cost. With no rate set anywhere labor counts as nothing and the work order says so. **Run `rails db:migrate`.**
- Localization settings work (Day 6, second half). Settings, Localization never worked: there was no server behind it. Administrators can now set the date format, 12- or 24-hour time, currency, number style and first day of the week, with a live preview, and they are applied: dates and times across work orders, PM schedules, assets, reports and settings, every amount (work order costs, parts, charts) in the company currency and number style, and the calendars and weekly reports start the week on the chosen day (**Sunday by default, as before**). The time zone is the one in Company settings. Everyone signed in reads the settings, only administrators change them, and changes are written to the audit log. The language choice was removed: there are no translations to switch between yet. Defaults match what the app showed before, so nothing changes until an administrator chooses.
- Production email now goes through a delivery method that reads the saved settings for each message (`FixflowMailDelivery`); the `SMTP_*` environment settings behave as before when nothing is saved.
- Photos and documents work offline (Day 14), and uploading them works at all. A photo taken without a connection is shrunk (max 1600 px, JPEG), kept on the phone, shown on the work order as "Waiting to sync", and uploaded when the connection returns; one sent twice (a reply lost on a poor connection) is stored once. **Run `rails db:migrate`** (`attachments.client_id`).
- Branding settings work (Day 6). Settings, Branding never worked: the page had no server behind it. Administrators can now set a logo, a favicon, one primary colour that restyles the whole app (the colour palette is now driven by CSS variables, with the shade ramp worked out from the chosen colour) and the headline and subtitle on the sign-in page. They are saved, shown on the sign-in page and in the sidebar, and survive a reload. The colour must be dark enough for white text (checked in the page and on the server), logos are PNG, JPEG or WebP up to 2 MB and favicons PNG or ICO up to 512 KB (SVG is refused, as it can carry scripts). The old sidebar and accent colour pickers were removed: nothing in the app used them. Reading the branding is public, as the sign-in page needs it.
- Uploading to a work order never worked: the web app sent the file under a name the server did not read, and the links to uploaded files pointed at `/rails/active_storage/...`, which neither the dev proxy nor the nginx configs forward, so they would not have displayed either. Uploads are accepted, and files are now served under `/api/v1/storage/...`. The server also checks uploads: 10 MB at most, photo / PDF / Word document only, and a file that claims to be a photo must really be one.
- Technicians can work without a connection (Day 13). Start, hold, waiting for parts, resume and complete, and comments, are kept on the phone when there is no signal, shown at once with a "Waiting to sync" badge, and sent in order when the connection returns (also when the connection drops mid-request). A status indicator at the top lists what is waiting, and anything the server refuses is shown with the reason instead of being lost. The queue is kept per person and survives closing the app. A comment sent twice (a reply lost on a poor connection) is posted once. Visited pages reopen offline over HTTPS: the offline cache now covers the API wherever the app is served from (it only matched `localhost:3000` before) and is cleared on sign-out. New: `comments.client_id` (**run `rails db:migrate`**).
- Internal notes never worked: marking a comment "internal" was ignored by the server, so it was saved as a normal comment and shown to technicians and requesters. It now works, and only managers and admins can add internal notes.
- Managers and admins now get an email when a part falls to its reorder point, and another if it runs out (Day 12). It is sent once each time stock newly crosses the line, whether from logging parts on a work order, adjusting stock, or raising the reorder point, so a part that stays low does not email on every change; restocking and falling low again alerts again. Deactivated people are not emailed. Needs email to be set up (`SMTP_HOST` and `SMTP_PASSWORD`); without it, the Parts page's low-stock filter shows what to reorder.
- There is now a Parts page (Parts in the sidebar, for technicians, managers and admins). It lists the catalog with search, a low-stock filter, stock status (in stock / low / out) and unit cost; managers add and edit parts, technicians and up adjust stock (add or remove, with an optional reason), admins delete. Stock changes, adds, edits and deletes are written to the activity log with who did it and the before and after. **Run `rails db:migrate`.**
- Parts are safer to manage: a SKU can be used only once per company (ignoring case; parts without one are fine; existing duplicates keep the oldest and get their id appended), a part used on a work order cannot be deleted (it used to silently remove the line from every work order and change their cost), costs cannot be negative, and the stock level can only be changed by adjusting it, not by editing the part.
- Logging parts on work orders works. It never did: the request was sent in a shape the server did not read, and the picker offered four invented parts. The dialog now searches your real parts catalog (new `GET /api/v1/parts?search=`), fills in the unit cost from the part, refuses more than is in stock, and logged parts can be removed (stock goes back). New `GET /api/v1/work_orders/:id/parts`. The PM "required parts" editor uses the same catalog. Parts have a unit cost now (**run `rails db:migrate`**).
- A work order's parts cost is now calculated. `work_orders.parts_cost` was never filled in, so cost reports always showed zero for parts; it is kept up to date as parts are logged and removed, and the migration fills in existing work orders.
- Running out of stock now answers "Only 2 each of Hydraulic seal in stock." (422) instead of a generic server error, and stock changes are locked so two people cannot take the same last part.
- Permissions: anyone signed in could create, edit, delete and adjust parts, and add parts to any work order. Technicians can now see the catalog and take stock, managers add and edit parts, admins delete them (the existing `PartPolicy` was never applied), requesters have no access, and parts can be logged only by a manager or the assignee, and not on verified or cancelled work orders.
- Preventive maintenance now counts completions. Nothing marked a PM execution completed when its work order was finished, so every compliance figure read zero. Completing a work order that came from a PM now completes its execution (and counts it on the schedule); sending it back reverses that; cancelling it counts the execution as skipped. Existing history is caught up by the migration (run `rails db:migrate`).
- The PM dashboard shows real data only. It used to fall back to hard-coded figures and a random chart (its endpoint did not exist, so it always did). It now shows loading, an error with Try again, and "no data" states, and compliance is nil, not 0% or 100%, until something has come due. Compliance is completed over everything that has come due in the period; skipped and past-due-and-undone count against it. New: change against the previous period, hours against estimate, a six month trend, compliance by location, recent activity.
- Fixed the PM list, the asset page's next-PM card and the schedule preview, which read the wrong response key or URL and would show empty. Skipping a PM execution now saves the reason you give (it was sent under the wrong name). "Run now" now honors the assignee, priority, due date and note you set in the dialog. The forecast timeline gets priorities.
- "Due this week" no longer counts schedules that are already overdue; they have their own list.
- Forgot password. New screens at `/forgot-password` and `/reset-password`, a "Forgot your password?" link on sign-in, and `POST` / `PUT /api/v1/auth/password`. The answer is the same whether or not the email has an account. Links work once and expire after 6 hours, and using one signs the person out everywhere. When the server cannot send email the screen says to ask an administrator, and admins can create a copyable reset link (Settings → Users → Reset Password, `POST /api/v1/users/:id/reset_password`), with the same safeguards as invitations: not for yourself, a deactivated person, or someone who has not accepted their invitation. Requests are throttled. `GET /api/v1/setup/status` now also says whether email is set up.
- Manage your team (Settings → Users): deactivate and reactivate people, change roles (one at a time or in bulk, all-or-nothing), and edit details. New `PATCH /api/v1/users/:id/deactivate`, `/reactivate`, `/role`, and `/users/bulk_role`, `/users/bulk_deactivate` (admin only; run `rails db:migrate`). A deactivated person cannot sign in (they see why), is signed out everywhere, and cannot be assigned work. You cannot deactivate, demote or delete yourself, and the last active admin cannot be removed. Edit User now saves name, phone, job title and department; before, the name was ignored. Removed the Reset Password action, which had no backend; it returns with the forgot-password flow.
- Security: **signing in no longer sets a session cookie that authenticates on its own.** Before, a browser holding the cookie stayed signed in after sign-out, a password change or deactivation, because only the token was revoked. Authentication is by token only.
- Security: the live-updates (WebSocket) connection now rejects revoked tokens and deactivated users, and rejects bad connections cleanly (its error handling referred to a class that does not exist).
- Company settings now work (Settings → Organization). New `GET` and `PATCH /api/v1/organization_settings` (read by anyone signed in, changed by admins only). Applied today: the company name, **time zone** (dates sent without an offset, such as report ranges, now mean the company's local time), **work order number prefix** (e.g. `MNT-000001`; changing it keeps counting), and the **default priority and due days** for new work orders that do not set their own. The PM, IoT, auto-close, working hours and holiday settings are saved too, marked "Saved, not applied yet" on the page. The unused `organizations` route is removed.
- Work order numbers now count up from the highest existing number instead of sorting the numbers as text.
- Fixed the organization page showing default working days and no holidays after load.
- My Profile now works. New `GET` and `PATCH /api/v1/profile` for name, phone, job title and department (new `users.job_title` and `users.department` columns; run `rails db:migrate`), and `PATCH /api/v1/profile/password`. Changing the password signs you out everywhere: every issued token is revoked, and the page sends you to sign in. Password attempts are limited to 5 a minute.
- The profile page showed a hard-coded organization name ("Demo Manufacturing Co.") for everyone; it now shows yours. The sign-in email is shown read-only, and the profile photo upload is removed until photos are supported.
- The web app now passes the TypeScript check (307 errors before), `npm run build` runs it again, and CI runs it with the web tests and build.
- Fixed work order checklists: ticking a step replaced the whole stored checklist with `{step, completed}`, wiping the instruction text and "required" flags, and the UI looked up items by fields (`id`, `description`) the API does not send. Updates are now merged by step.
- Fixed the asset IoT page passing metric names to a chart that needs each metric's readings, which would throw for any asset with sensor data.
